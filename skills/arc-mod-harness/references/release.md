# 从选定候选到朋友能装的包

## 明确替换范围

默认优先**按原角色的真实资源路径 Cook、打 PAK，由游戏直接加载替换**，复用已有模型、
材质、动画及显隐入口。确需额外组件或现有入口无法表达的控制时，再为这部分增加新资产
入口或零售运行桥；逐项记录原因，不因编辑器里拆了显示层就把整个人物改成动态装配。
开发工程每帧驱动不会随 Cook 自动进入 Shipping。立项时先完成包含
实际消费者、材质、动画、所需物理及显隐的最小零售闭环，再扩展全部角色内容。
详细步骤、R09.3 历史证据、R210 新路径对照和合成安装演练见
[cook-install-example.md](cook-install-example.md)。

为每类资源填写 `templates/replacement-matrix.md`。不要只列“模型”和“贴图”。
通常还要调查 high/low/LOD、阴影/轮廓 pass、分身、道具、独立材质实例、每套配色、
动画变体、声音事件、语言、文本/UI 和脚本。未改的游戏原生资源只记录，不无差别打入包。

`dependencies` 表示运行时加载关系；`built_from` 表示制作来源。二者必须分开：
FBX 是 uasset 的制作输入，不是朋友需要的运行依赖；自制 ILM 是材质的运行依赖，不能漏。
工具从显式 runtime 根节点沿 dependencies 找闭包，只收 selected variant 和 shared。
原生依赖需要匹配游戏版本的查询证据；外部依赖尚未提供时不能谎称是完整独立包。

## 发布检查次序

1. 冻结选定候选和所有输入。其他方案保留为 archive/review，排除在运行根节点之外。
2. 用实际 Cook/打包工具生成产物；记录资源挂载名、所有 companion 文件与哈希。
3. 从最终 PAK 再列出并提取，核对运行文件、引用闭包、路径大小写及重复覆盖。
4. 检查包中不含作者工程路径、调试素材、其他方案、训练模型或临时输出。所需非原生
   最终资源全部纳入；借用资源的发布资格与来源明确，不能由“下载得到”推出“可再发布”。
5. 安装到已授权位置；旧版备份在整个 Paks 树之外。保留无关 MOD、管理器配置，分别核对
   live 与管理器 library 哈希、当前 loadout 和所有相关 PAK 启用键。
6. 在实际游戏中测试明确列出的颜色、关键动画、语音、武器和冲突。标出未覆盖部分。
7. 朋友测试使用分享压缩包，记录游戏版本、语言、加载器、包哈希、测试场景和报错。
8. 以最终真实渲染/捕获导出封面与配色展示，附源帧/hash。公开发布及发消息遵循实际授权。

不能把 SIG sidecar 的兼容用途称为新生成的密码学签名，也不要把包解压 CRC、安装哈希、
线上一键安装和实机试用合成一句“所有验证通过”。分别记录。

## 版本和审查状态

`release-plan` 可以为尚未完成实机测试的候选生成清单，会明确标成计划。`check --ready-for
local-test` 要求相关制作及 package 审查记录有效；`--ready-for share` 还要求对应 runtime
审查；`--ready-for friend-verified` 再要求朋友环境证据。它检查的是**记录完整性**，不是
独立证明记录内容为真。没有实机能力时可以交付标明限制的试用候选，不可声称实机已过。

## 可回收空间

先统计重复提取、旧帧序列、重建缓存等大项。保护当前制作源、选定/保留方案、已交付包、
审查视频、关键帧、参数和版本清单。只在明确用户授权范围内删除已经可重建且不再需要的
文件。用确切文件和哈希生成清单，执行前再验路径不越界、无符号链接/junction。

本仓库的 `clean-plan` 不删除任何内容，只列 role=temporary、无依赖/审查/反馈引用且
未变更的文件；执行删除需要另一个经过检查的实现。不要仅按“临时目录”“旧日期”判断。
