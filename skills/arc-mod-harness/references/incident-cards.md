# 可照着排查的故障案例

阅读方式：先找到相似症状，复现原问题，再用证据选择修复层。H 编号对应本仓库历史来源
索引。下面的参数、骨名和时间段只解释 Chaos 当时怎么做，不能直接当新角色修复脚本。
完整媒体保留在原生产工程；公共仓库提供过程和证据索引，不附原游戏资源。

## A. “下眼缘太拱”，结果把上眼皮拉坏

**问题是什么。** 作者要整个眼睛下方边缘更平，保留半睁的慵懒感，并能看见黑瞳孔。
候选却改变上睑/睫毛，眼裂变窄，黑瞳孔被藏住。眉的局部弯折与眉下阴影又放大了怪异感。
这包含轮廓、遮挡和明暗三个问题，不能用“把眼睛压扁”一次概括。[H12–H15，作者反馈]

**先前为什么失败。** 把邻近控制骨或无序顶点编号当作“下眼睑”；把“死鱼眼”理解成更小
开口；认为镜像位移就会有相同神态。下睑、眼角、眼白、虹膜、黑瞳孔实际是不同对象。

**定位步骤。**

1. 冻结作者指出的动画和完整相机画面，记录 high/low、源 key、输出帧的对应。
2. 从当前最终拓扑、实际权重和 rest 重放姿态，分别标 `eye_rim_lower/upper`、`iris`、
   `black_pupil`、`brow`。使用真实边连接；无序点只画散点，不能按编号顺序连成轮廓。
3. 把当前轮廓和参考下缘投到同一图里。先回显“准备改的是这条线”，让作者能指出选错对象。
4. 若是眉下暗线，单独看面部控制色与实际 shader；它不一定是多了一条几何眉。

**实际修复路线。** 先恢复不应改变的上睑，把下缘目标设成接近平直、两端自然回到眼角；
眉与眼共同拟合所选神态。虹膜位置/大小与黑瞳孔可见性分别检查。眉下固定阴影的一个
具体候选只选择基础脸面、眉骨权重质量大于 0.10 且原 R 小于 0.99 的角点，把 Color.R
改为 1；其余 GBA、位置、UV、法线、权重和 rest 保持。它是当时已定位区域的控制色修复，
**不能推广成“所有眉阴影都把整脸 R 设 1”**。[H13]

**怎么复查。** 原生导入/Cook 读回受保护字段；同相机看全脸与眼眉局部，确认选中下缘
真的改变，上睑未被误改、黑瞳孔能看清。再看眨眼、转头及相邻帧。作者选择气质，AI 先
清理明显扭曲/破面；后来的 A/B/C 由作者选 C，保留其余而不入包。

**下一项目怎么用。** 复用“分组—目标投影—约束—实际渲染”的方法，不沿用旧顶点号、骨名
或某个坐标。算法只证明点去了哪里，最终是否呆、疲惫或挑衅仍需人看整脸。

## B. 入场少数帧瞳孔破碎、消失

**问题是什么。** 静态看眼睛还正常，入场几帧青色虹膜/黑瞳孔呈碎片甚至像空白眼。
这很容易被误诊成贴图漏包。[H06、H12]

**诊断与排除。** 重放原瞳孔独立缩放和当前 high/low/头部层叠；投影黑瞳孔三角，并用
采样射线比较眼白表面深度。实际诊断跨 401 帧，问题路线指向特定姿态的眼白遮挡和间距，
不是仅靠替换颜色能够修复。早期脸工程的间距修复并不自动覆盖后续新总装和新原生权重。

**怎么改。** 在独立候选中调整相关眼内表面的局部间距/前后关系，保留眼眶与已选表情，
按真实瞳孔尺度复测。不把“黑圆没出现”一律当缩放太小，也不将整个眼球前移到眼睑外。

**复查与下一步。** 检查整段入场中黑瞳孔可见、眼白与虹膜不相互穿出，附失败帧前后。
闭眼时正常的遮挡不用修成一直可见。若深度关系正确仍有碎裂，再排查三角面朝向、近裁面、
材质透明度或实际显示对象；不要反复沿同一方向加距离。

## C. 胜利末帧嘴好看，中间讲话却穿唇

**问题是什么。** 作者同时提出双眼看点不统一、眼镜桥挡成假嘴、嘴歪。早期候选只调最后
画面，末帧改善了，但常量嘴位移套入原说话姿势后，上下唇会交换或局部脸面反转。[H18–H24]

**为什么第一轮修复不够。** 胜利头在倾斜，屏幕中的水平不是头部的水平；high/low 的原
嘴高度也不同。把 high 的绝对位置给 low，或将最终浅笑的位移加到整个后半段，都可能错。

**实际收敛过程。**

| 候选阶段 | 改了什么 | 发现什么 / 下一步 |
|---|---|---|
| 早期瞳孔/眼镜调整 | 先调注视与镜架位置 | 嘴暴露后形状需要独立修，不能只移眼镜 |
| 末帧常量嘴位移 | 把最终目标加到其他晚段姿态 | 讲话过渡出现上下唇错位；改用各自原始姿态 |
| 相对基线和逐姿态拟合 | 各头独立基线，围绕头中线形成浅嘴线 | 仍出现局部面翻转，需要几何约束 |
| 限制面朝向 | 加入原面法向方向的约束 | 不翻面仍可有负唇间距，必须再加独立约束 |
| WinHarmony06 | 按姿态同时约束面朝向、唇间距和局部位移 | 形成最终候选，做原生读回与连续视频检查 |

**求解到底在做什么。** 在当前头部参考平面里，用实际原生 byte 权重构成选中嘴控制对
嘴缘的影响矩阵。每帧让控制位移尽量逼近该帧目标，同时惩罚无必要的大位移；限制受影响
三角相对原面的朝向，并在嘴宽方向采样上下唇间距。目标通过过渡包络逐渐生效，不能突然
跳到末帧。实际脚本使用 SLSQP；嘴外控制、原 Q/S 和不变前段分别做保护。[H24]

可复用的思路是以下伪代码，**不是可直接运行的游戏适配器**：

```text
for each affected source key:
    restore that head's original pose
    project current rim in the actual head/camera frame
    target_delta = transition_weight * (target - current_rim)
    solve selected local translations:
        minimize target error + displacement penalty
        constrain affected face orientation and upper/lower lip gap
    validate all affected faces, not only the active solver subset
export allowed channels; read back native saved/cooked data
render the entire transition with the actual camera and matching voice
```

**验收的精确边界。** 最终动画有 592 个原始 key，末 121 key 的局部求解对应 471–591；
原 key 与 593 帧输出视频序号不能直接混用。视频记录对变化末段 137 帧逐帧目视。局部
面朝向检查不代表所有三维自交为零，原生读回不代表新实机已测。保留这些边界，不能只写
“嘴彻底修好、所有帧完美”。[H19、H20、H23、H24]

## D. 身体改窄了，原动作的肩膀/手位却不对

**问题是什么。** 新身体在 rest 能看，但套原 COS 动作肩臂显宽。缩网格/改权重几次后
作者仍觉得不自然。继续压上臂会把动作比例问题变成身体畸形。[H08、H30–H34]

**如何定位。** 同一新身体分别播放原姿势与参考比例姿势，画肩、肘、腕和手的骨轴位置；
区分皮肤到骨的蒙皮关系与骨链本身的偏移。四条锁骨/上臂根平移的 Ref075 是项目候选，
不是“所有女体都缩成原肩宽 75%”的公式。

**怎么修以及第二个问题。** 调整视觉肩臂比例后，胜利手靠脸的位置又发生变化；原手位在
窄肩和保留臂长的条件下并非所有时刻都可达。因此对胜利晚段单独做接触恢复：每帧先回
原 COS800，再应用冻结的比例适配；0–432 不操作，432–480 平滑进入，480–591 保持
原双手的位置与朝向。旋转修正只涉及两边上臂/前臂/手，保留手指握姿和原臂长。

这里实际允许四条 T 和六条 R，不代表全 R 都未改。时间、曲线、事件、其他通道和源 rest
独立守卫；枪在枪套的片段不附加手链位移，持枪片段另查武器配对。

**复查。** 不只看最后手碰脸，检查入段邻帧的手速、肘弯方向、袖口和完整构图；实际保存、
Cook 与压缩采样验证另做。134 条原生候选中 POT 压缩减键的例外保留旧失败和有界差异，
不改公共容差来抹掉它。134 条数据检查不升级成全 134 条实机玩法验收。

**给新作者的决策。** 先找体型合适且已适配目标角色的基础身体；原动作自然时直接复用。
只有证据显示比例/接触问题才走上述动作路径，不让每次换衣服都变成全动画重定向。

## E. 所有配色的枪突然变黑

**问题是什么。** 作者在实际游戏中发现枪变成黑色剪影，多个配色同时出现；身体主体仍
有颜色。这个分布提示应先查武器共用资源，而非分别修每套配色。[H11]

**定位与修复。** 沿枪的运行材料实例和父链查询实际 Detail 参数，发现身体图集变化影响
同名共享输入。保留原枪需要的 detail 为独立 `COW_detail`，重定向枪相关继承链、配色、
效果和翻转等变体；身体继续用新布局。不能仅把某张枪 Base 涂亮，或只修 Color01。

**怎样证明修在正确层。**

1. 包内确实包含新独立图及所需 companion 文件，挂载路径与实例引用匹配。
2. 旧身体相关输入保持，枪实例能解析到正确原语义；没有某个父实例继续指向新身体 Detail。
3. 用默认色、差异最大的颜色先看枪/枪套/特效状态，再核全目标配色。
4. 安装最终包后按作者出现问题的实际动作检查；旧版截图不能代替新包。

**通用教训。** 依赖存在并不等于依赖正确。声明图能找缺项，还需实际材料路由和视觉检查
才能发现“文件名相同但 UV/内容语义换了”的问题。

## F. 纹理、UV 和材质：三种相似花块，三种原因

这些问题的完整证据在 [表面专题](texture-uv-material.md)，这里给出诊断分岔：

| 真实问题 | 最小区分实验 | 实际修复 / 边界 |
|---|---|---|
| 胸口细节锯齿，8K 合图也无助 | 同模型/镜头，对比硬分色与保留原连续 AA 的源查询 | 从源重采样并分配有效像素；不能恢复原素材不存在的小字细节 [H37] |
| 原生预览大片色带 | 同场景读实际驻留 mip，普通启动与完整驻留 A/B | 定位 64×64 startup mip；隔离禁 streaming 只作诊断，游戏预算另验 [H38] |
| UV 零重叠仍有图案异常 | 检查全部域界与保存后 UV，不能只数重叠 | R05 出界被拒，R06 完整选择排布和读回；作者 UV 通过不等于成品材质通过 [H39] |
| 外套低密度材料边界串色 | 真实相邻边的材料归属与已烘 ID 逐面比较 | 有问题的 541 面局部留足采样格，保留好岛，重查真实覆盖 [H41] |
| 手边缘发黑 | 排除无命中子样本后对比 RGB 均值 | 有效样本采样；AA 覆盖 alpha 不覆盖游戏控制 alpha [H42] |
| 发梢小黑点 | 看真实源纹理覆盖，不用纯黑填未查询点 | 修实际头发纹理覆盖；通过的是 4K source-base 阶段 [H43] |

不得因为最终都叫“花块”，就统一改法线、扩大图或模糊边缘。每次最小试验只动一个可解释
变量，保留不成立的猜测和它被哪条证据否定，后人才能避免重新走同一弯路。

## G. UnrealPak 是命令行工具，却向作者弹出插件错误

**症状与输入。** Gold Ship 项目读取作者提供的丝袜参考 PAK 时，匹配 UE 工具的 `-List`
调用未传 `-unattended`。作者截图显示 `XboxOneZlibCompressionFormat` 模块缺失的模态窗口。
该包实际使用 Zlib，列表随后得到 45 个文件；窗口不是资产损坏的证据。

**被否定的假设。** 命令行程序、stdout 重定向、隐藏控制台或 `-nopause` 不保证 UE 不弹
消息框。缺失插件警告仍可经过 `FMessageDialog::Open` 打开 Windows 对话框。

**区分证据与修复。** 读取匹配引擎的 `Runtime/Core/Private/Misc/MessageDialog.cpp`：
`FApp::IsUnattended()` 控制弹窗分支，提示仍写入日志。修正启动参数为 `-unattended`
并用隐藏进程、参数列表和 60 秒超时启动，未改引擎或其他任务的项目配置。

**实际复查。** 同一输入 PAK 在约 0.92 秒完成提取，exit 0，实查 45 个落盘文件并记哈希。
缺失模块诊断仍在日志中，因此结论是该次 Zlib 提取完成、对话框按源码转入无交互分支；
没有声称插件已安装，也没有把源码分支检查说成桌面画面观察。私有项目证据为
`source/stockings_reference_r161/extract_report.json`，不在公共 harness 分发该包或引擎文件。

**作者要求与复用范围。** 作者明确要求把注意事项写进同类项目规则。复用的是后台 UE
工具无交互启动、依赖诊断与实际输出检查；不将“这个 Zlib 包能读”外推到其他压缩格式。
作者需要交互编辑器的工作流不强制无交互；其他工具是否支持同名参数应先核实。

## 新问题如何记录成同样有用的案例

每次选定路线后，补下面八项。作者只提供截图、想要的变化和主观意见，技术记录由 AI 填：

1. **现象：** 哪版、哪个实际镜头/帧/颜色、哪个部件，和目标差在哪里。
2. **输入：** 模型/拓扑/UV/材料/动画/相机的确切版本与哈希。
3. **失败假设：** 试了什么，为什么当时合理，哪项结果证明它不够或不对。
4. **定位证据：** 哪个最小 A/B 或实际数据把原因收窄到哪一层。
5. **修复：** 具体选择区域、变换/采样/路由规则；影响哪些字段，保护哪些字段。
6. **复查：** 保存读回、原生/Cook、实际画面、完整过渡、相关配色/消费者分别怎样测。
7. **人类决定：** 当时实际原话和看到的候选；技术 PASS 不替人作审美批准。
8. **边界与复用：** 还没测什么；哪些方法可复用，哪些数字、骨名和点号只属于该次工程。

如果没有找到根因，写“当前假设”和下一项区分实验，不先把尝试包装成成功案例。
