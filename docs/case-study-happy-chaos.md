# 一个综合角色 MOD 的 3–4 天：从“想做成这样”到可以交付的候选

本文根据作者与 AI 的制作交流，以及 25 份实际工作记录整理。**3–4 天是作者对投入时长
的概括，不是工具计时统计**；文件记录跨越 2026-09-10 至 09-15 的多个检查点，不能把
日历跨度、后台渲染时间和人的实际工时混为一谈。下面按制作阶段复盘，不编造逐日工时。

记录索引见 [case-source-ledger.json](case-source-ledger.json)。H01–H25 指向原工程的相对
文件名和本次读取的 SHA-256；原文件、游戏资产和完整私人对话不在公共仓库中。这些是
可供作者回查的证据索引，不声称外部读者已经能独立重跑全部生产工程。

## 1. 怎么立项：愿望先于清单

目标最初不是“换一个 FBX”，而是把 Happy Chaos 做成作者提供插画里的可爱成年女性化
形象，同时保留角色辨识度：蓝灰皮肤、青绿眼、浅金色蓬松刘海和高马尾、小角、光环、
眼镜、皮肤纹样，以及短上衣、热裤、滑落肩的宽松外套。作者特别重视脸的气质和身体曲线。

开头先分析已有复杂替换 MOD 与原角色资源，保存原模型和骨架基线；再用 image gen 的
生成/编辑做完整正侧背概念。第一张插画没有完整脚部，AI 初稿用赤脚补全，作者明确不喜欢。
后续借鞋模型参考补为运动鞋，又把红色改为奶油/暖杏色、去掉标志。这揭示了第一条教训：
**AI 对缺失部位的补全只是提案，不是需求。** [H01–H04]

概念经历 V01–V04，逐步补齐高束分层马尾、短裤细节、鞋袜与 T pose。后续作者又提出
窄胯、自然无唇彩、缩短颈部、完整后脑发层。这些更新优先于已经保存的概念图。因此真实
规格不能只是“一张最终参考图”，还需要简短、持续更新的保留项和修正记录。[H01、H03]

如果重来，立项会更早输出一页 brief：目标、不可改坏的部分、未决定的补全部位、最重要
的游戏镜头、替换范围和交付方式。用三个问题开局，再靠图片追问；不让新手一次填写几十
项骨架和材质参数。

## 2. 怎么开头：2D 定意图，3D 解决结构，工具链先跑小闭环

作者提供多个类似角色/MOD 的模型包，让 AI 检查实际几何、UV、材质和绑定。马尾参考
帮助确定头发结构，Jam 相关模型提供身体、衣服和鞋的可研究或适配结构；其他角色用于
肩臂比例、复杂改模组织方式等对照。不同参考的用途不同，不能整个人物一股脑照搬。
本项目历史包含真实供体几何适配，也包含只读研究；harness 要分别记录来源与使用方式，
不能把“只参考”写成所有历史操作的统一描述。[H02、H05、H06]

初期按身体/短裤、脸、服装配件和工具链拆分工作，保留原 COS 骨名、层级与 rest pose，
再把造型、UV 和权重适配上去。每次保存真实 Blender 三视图和脸部特写，与概念并列。
生成图负责回答“想要什么”，真实网格负责回答“已经做成什么”。[H03–H06]

工具链也有早期障碍：最初指定的开发目录不完整，另一个安装目录是不同大版本引擎，
后来才定位匹配的 UE4.25Plus。先做原模型导出→Blender→ASW FBX→原生导入→Cook→
读回，可以提前发现这类根本兼容问题，而不是建完角色后才发现包不能使用。[H04、H09]

## 3. 实际要替换什么

一个角色由多个运行对象组成。下面是此次项目需要考虑的资源，不是所有游戏的固定列表。

| 类别 | 为什么不能只替换主身体 |
|---|---|
| 身体、外套、头发、鞋、配件 | 有独立网格、权重、slot 与阴影/轮廓数据 |
| high/low 头及特殊显示部分 | 战斗和电影镜头切换不同对象；只修一个会在另一场景回退 |
| 眼白、虹膜、黑瞳孔、眉、嘴唇、牙舌、口腔 | 各自受不同控制与遮挡影响，不能用一个“眼睛/嘴”标签笼统处理 |
| 枪、枪套、光环、分身等 | 可由独立资源/材质/动作驱动，不随主模型自动更新 |
| Base/SSS/ILM/Detail/OLM/Decal 与材质实例 | UV、颜色空间、alpha 和共享引用共同决定实际外观 |
| 所有目标配色 | 肤色、衣服、鞋和眼镜都有分配关系，不是只改一张 base 图 |
| 视觉动作、面部动画及其变体 | 新比例需要适配，但原时间、事件、曲线、挂点和逻辑不能随意改 |
| 语音目标及语言/事件映射 | 替换音频必须进包，并在对应动画和实际触发中试听 |
| 打包所需 companion 文件、非原生依赖 | 本机制作工程存在的文件，朋友电脑不一定有 |

最后 R09.3 的包清单为 **1,169 个资源、2,417 个运行文件**，保留 **19 套配色及 703 个
Frau +12 日语语音目标**。目标事件数不等于不同录音数；语音处理模型本身不需要随游戏包
交付。这些数量来自本次项目，不能写死到通用 harness 的“完成”标准里。[H18、H21]

## 4. 反复返工，不只是“AI 不够会建模”

主要困难是跨层问题：造型、拓扑、蒙皮、原动作、原 shader、Cook、游戏脚本和人类审美
互相影响。一个层面的修复会在另一个层面暴露新问题。

### 连续身体与肩臂：局部数值变好了，整体可能更差

胸腹腰部曾尝试拼接不同来源的身体，再增加接带采样、调整曲率与法线。反复补窄带难以
恢复原来连续的曲面和变形关系。只读研究完整 Jam 身体后，能看见胸下、肋腹、腰和髋
原本是连贯表面；人为截口让一小段连接带承担两套曲率、法线和权重的差异。路线转向
更完整的连续身体适配，而不是继续堆接带补丁。[H07]

肩膀在动作里过宽也曾尝试局部缩形、改权重。作者否决：数字变窄，但身体更不自然。
后续改为研究相似角色骨轴和父子偏移，协同调整视觉动作比例，并复核晚段手靠脸和原枪
接触。**静态人体适配和动作比例适配要分开判断**；不能把动作问题都压给网格。[H08、H10]

通用路线应是：连续 nude rest pose → 人体比例审查 → 衣服 → 骨架/动作适配。实际项目
最初做了较多拼接和并行整合，后来才逐步转向这条更稳的路线；不能把理想流程冒称为
从第一天就完全遵守的历史。

### 原生管线：查看器输出不等于游戏真相

全局 inverse bind 看起来正确时，仍可能存在 root scale=100、子位移缩小的抵消。
最后通过导出副本的厘米制转换和原生每骨局部 T/Q/S 检查定位，避免改坏源模型。[H09]

权重也不能只看查看器导出的四组：实际原生路径支持更多影响，导入会过滤很弱的权重并
量化为 byte。为了修正引擎变形，需要读取真实原生数据、匹配控制点/三角形，再用量化后
权重评估实际姿态。换了拓扑后沿用旧点号、借另一份头动画、重复叠加电影 HeadLink 都会
让“检查”本身测错对象。[H09、H10]

材质往返中也遇到导出查看器对 alpha 的表现与实际源像素不一致。解决方式是分清源图、
原生导入数据、GPU 压缩解码的职责；不能拿一个查看器导出的 PNG 宣称整个通道丢失，
也不能把有损压缩结果声称为逐字节无损。[H09]

### 黑枪：遗漏的是共享关系

作者实机发现所有配色的枪都变黑。根因路线指向共享 detail 输入：身体使用新布局后，
枪材质仍依赖同一个原始名称。修复把枪需要的原 detail 独立为 `COW_detail`，在枪材质
链中重定向相关引用，覆盖配色和特效/翻转等变体；不是单纯把枪重新涂亮。[H11]

这说明打包依赖齐全还不够：**引用存在但指向语义错误的共享贴图，也会出错。**
需要资源关系、实际材质画面和实机观察一起检查。

### 眉、眼、瞳孔：用户说的对象必须映射到正确控制组

眼睛是返工最多的区域。作者先追求慵懒表情，后来又想比较早期较戏谑的方案；多次明确
“下眼皮太高”“整个下边缘太拱”“上眼皮被拉坏了”“眉毛中间弯”“瞳孔要清楚可见”。
这些不是同一参数的增减，而是不同目标：眼眶轮廓、上下睑、虹膜、黑瞳孔、眉和眉下阴影。

AI 曾把“死鱼眼”过度理解成缩窄眼裂，把黑瞳孔藏住；把下边缘问题改到上边缘；机械
移动瞳孔后又出现视线不一致或斗鸡眼。作者提供参考图、局部截图和归一化点位，多次纠正
具体对象。真正有效的转折是作者要求**先画目标控制点的 2D 投影，再调整 3D**。

投影也不是画出来就对：边界点数组可能无序，按编号连线会乱；坐标上下方向和镜头旋转
可能反；虹膜中心不能代替黑瞳孔中心。最后用真实网格、原生权重、实际动画和源相机，
分组绘制当前点与目标点，配合完整画面判断，再做限定范围的变形。[H12–H15]

眉毛形状和异常阴影分别检查。除了骨控制，还检查镜像后的面绕序、法线及眉周固定阴影
控制色。形状修完后仍要看原 shader，不能让一条扭曲阴影继续让平眉看起来弯。[H04、H13]

作者最终通过三种原镜头视频选 **C / Compact01**，保留 A/B 本地备选但不放入运行包。
这是人类最有效的审查方式之一：有明确差异、同一镜头、可播放的几个候选，决策可以
追溯到“我比较喜欢 C”。[H15、H21]

### 入场和胜利：静帧好看不能替代过渡检查

入场中只有几帧瞳孔碎裂或消失。诊断重放真实缩放/层叠，比较黑瞳孔三角采样与眼白的
相机投影深度，定位遮挡/间距问题。外套腋下黑块则需要分辨内外层穿插、权重和阴影，
按举臂原镜头修局部，不能一律归为“缺贴图”。修复后查看连续区间。[H12、H14]

胜利结算末段又出现眼镜遮嘴像“假嘴”、两眼看向不同方向、嘴歪。我们先生成整体参考，
但 AI 参考也额外改变了眼裂和嘴型，因此只借局部方向；它从未进入运行包或作为发布截图。

最后嘴部修复是典型的“修了又出现新困难”：

| 尝试 | 新暴露的问题 | 改变路线 |
|---|---|---|
| 移瞳孔、上移眼镜 | 嘴仍太开、倾斜 | 单独建立嘴的头平面目标 |
| 把最终微笑的常量位移套入末段 | 中途说话时交唇、重新张开 | 各帧按当前姿态拟合，再平滑融合 |
| high/low 共用绝对位置 | 两套头的嘴基线不同 | 相对各自原嘴高度与尺寸拟合 |
| 调正嘴角与浅弧 | 局部脸面仍翻转 | 加表面朝向约束 |
| 只有“无翻面”约束 | 上下唇仍可能交叉 | 同时约束面朝向与唇间距 |

最终 WinHarmony06 在末段只调整明确的瞳孔、眼镜和嘴控制平移，保留旋转、缩放、不
相关通道以及前 0–470 keys；原生/cooked 读回核对。几何审计报告局部嘴面零法向反转，
最终中央唇间距为正；过渡早段仍有极小的采样负间距记录，不能把它写成全模型数学意义的
绝对无自交。受影响末段的实际画面未见前述破口与翻唇。[H19、H20、H24]

## 5. 材质、配色和语音并不是最后随便附上

作者认为身体是最好的一部分，但腹部和大腿缺乏皮肤光泽，提供了 Jam 高光参考包，让 AI
查看真实贴图/材质。此阶段研究其实现，修在本项目自己的图集；不是把参考包整个复制进
MOD。高光相关通道局部调整，同时保持不相关阴影/黑线和 alpha，再核对 Cook GPU 解码。
鞋面跟随服装色、鞋底/鞋带保留浅色层次，眼镜恢复原配色分配；全色集一起检查。[H16、H17]

语音是作者另行做好的 Frau epoch200 +12 转换，并给出整合说明。作者还提醒审查视频
必须带对应修改语音。这把“声音文件在目录里”提高到了“目标事件映射、打进包、按原触发
时间试听”。引擎预览中的事件对齐配音与实机声音录制仍是不同证据。[H14、H18、H21、H23]

发布图也调整了顺序：先解决材质/表情，再生成全配色和战斗动作图片；作者指出身体完成
度高，应该多展示动作而非只盯脸。展示内容的选择同样是人类对作品重点的判断。

## 6. 最合适的检查方式

不是“所有东西每次全测”，而是按风险逐层回答问题：

1. **概念与人体：** 正侧背、脸部近景，跟作者参考并列；必要时无衣身体与线框看连续性。
2. **技术结构：** 真骨架、局部 bind、slot/UV、法线/颜色、原生权重和 Cook 读回。
3. **早期修复：** 最能暴露问题的原相机关键帧 + 邻帧 + 2D 投影，快速淘汰错误路线。
4. **修复收尾：** 受影响动画连续 contact sheet，异常处原分辨率放大，正常速度完整播放，
   带对应语音；记清实际检查帧区间，不把生成帧数冒充看过的帧数。
5. **配色与共享资源：** 默认/极端颜色先验证机制，最终所有目标颜色检查武器、鞋、眼镜
   与肤感。改变共享材质时查所有消费者。
6. **交付：** 依赖闭包、包提取/hash、安装/hash、管理器 loadout、实际游戏、朋友机器
   分开记录。最终封面从当前真实模型/包对应的渲染或捕获导出。

本次 R09 的五段原生预览记录了 1,645 帧的连续审查；后续 R09.3 对胜利变化末段审查了
137 帧，视频本身有 593 帧。不能据此推导所有颜色、动作、对手和游戏脚本都穷尽检查过。
最终 R09.3 的记录明确是原生 UE 源相机预览，不是该版新实机录像。[H14、H23]

## 7. 人类到底贡献了什么

作者并不是简单点“批准”。人类提供了五类 AI 很难自行补全的信息：

- **审美与反例：** 对赤脚、胯宽、颈长、唇彩、眼神、嘴歪的具体不喜欢；这些限定了目标。
- **高价值材料：** 插画、类似 3D 模型包、原 shader 参考、已完成的语音及其整合说明。
- **实际使用证据：** 游戏中的黑枪、入场瞳孔消失、外套黑块；AI 的离线审查没有覆盖到。
- **方法纠正：** 明确“下边缘”“黑色圆形瞳孔”，用点位标图；要求先投影后变形、按游戏
  相机看、逐帧检查。这直接改善了 AI 的问题表示。
- **取舍与交付决策：** 选 C、留 A/B、不混包，要求全非原生资源随包、Unverum 安装、
  语音入视频、先材质再封面，最后允许清理确认无用的中间产物。

AI 更适合负责资料查找、实际网格与材质研究、脚本变形、求解、批量导入/Cook、依赖和
哈希核对、候选渲染、整理审查页。人类应在目标成形和重要候选出现时介入，**看到具体
结果后做选择**。不应被迫先猜骨头和参数，也不应等整包完成才第一次看到游戏镜头。

## 8. 最终状态与还没证明的部分

R09.3 已打包并在本机安装、登记到已有 Unverum loadout；保留旧版，核验未改动无关 MOD。
相对 R09.2，仅两个胜利 high/low 动画资源、四个运行文件变化，其余 2,413 文件保持相同，
保留 C 必杀表情、枪材质修复、肤感、配色及 703 语音目标。[H18、H21]

最终还导出了 8 张原生高清展示图。**没有最终 R09.3 新一轮实机测试、朋友物理机器验收
或公开 GameBanana 一键按钮测试记录**。历史 R07/R08 有用户实机反馈，但不能挪用为
R09.3 的通过证据。包布局/管理器复制规则模拟与真正在线安装要分开写。[H04、H18]

清理按明确文件与保护哈希执行，删除已确认的重复解包、试验帧和派生缓存，逻辑移除约
30.77 GiB，保留源文件、旧包、A/B 与关键审查证据。后来产生的新渲染会占回空间，因此
这个数不等于今天磁盘净空闲增长。[H22]

## 9. 这些经历怎样变成 harness

| 这次损耗 | harness 中的具体机制 |
|---|---|
| 需求藏在长对话里，旧参考又被当新目标 | 渐进问答 + brief + 保留项 + 明确新决定 |
| 没有素材就硬猜结构 | 三视图 gen/edit、实际 3D 参考用途与来源清单 |
| 身体边做边拼，衣服掩盖问题 | 连续 rest pose 的独立审查，再穿衣和动作测试 |
| 指错眼缘、瞳孔含义不一致 | 控制组命名、点击反馈、实际 2D 投影图 |
| 只修最后一帧 | 同镜头短视频、变化区间与两端连续审查 |
| “通过”到底是哪个文件说不清 | artifact/hash/built_from、过期决策检测 |
| 旧截图配新包、A/B 混进 C | 选定 variant、运行闭包、包与实机证据关联 |
| 新手不会提供可执行反馈 | AI 追问并代填部位/镜头/目标/保留项 |
| 所有工作都要人盯或等人许可 | 审美选择才请求人决策，已授权技术工作自主推进 |
| 缓存巨大又不敢删 | 明确 temporary 分类、引用保护、只读清理计划 |

本 harness 将这些方法实现为技能、模板、可运行的记录与审查工具，以及故障演练。
它没有把案例里的某个骨位移、贴图数值或 UE 版本冒充万能算法；最重要的可复用部分是
**先让目标可见，再让每次修改与目标、输入和实际检查对应起来。**
