# Cook → 原路径 PAK/SIG → 手动与 Unverum 安装实作例

本例把 Happy Chaos R09.3 的历史证据与可复用步骤分开。真实来源只登记相对标识和
SHA256，见 [cook-install-evidence.json](cook-install-evidence.json)；不附游戏资源或本机目录。
下文“R09.3 已做”来自历史脚本/结果；“复用时”是新项目应适配的合同。

后续 [R214 全配色与便携迁移实作](gold-r214-color-transition-example.md)第 9 节补充单 PAK
分发、当前目标 SIG、按旧收据退役、同 hash 预放文件归属、旧版叠装拦截与 28 项
Windows PowerShell 合成检查。合成测试、真实安装和用户游戏验收分别记录。

## 先决定谁会消费资产

**默认选原路径资源替换。** 对模型、材质、贴图和动画，先找当前角色实际消费的
package/object 路径，在兼容工程中制作对应资产，Cook 后按该路径打入 PAK，让原游戏
继续负责创建角色、播放动作及常规显隐。先验证这种最小改动，额外组件确有需要时再接入。
这也是本项目作者明确选择的交付原则，不是禁止所有运行扩展。

这项选择在**项目开始时**完成。作者提供 UE 工程，首先用于核对原角色目录、对象名、
骨架与材质 section、描边 pass、AnimArray/AnimSet、AnimBlueprint 和兼容 Cook 方法，
不能据此默认转成另做一套开发演示装配。这里的“覆盖原文件”指 MOD PAK 在原逻辑路径
提供替代资源，原游戏主 PAK 保留。先做一个实际可见的最小覆盖，确认游戏确实消费它，
再扩展制作量；额外组件的必要性逐项说明。

### 反例：做完了，却没有被最终游戏调用

R210 的入口核对找到105个已制身体动画资产：99个主动作、1个独立自然身体变体、
5个入场动作。此前零售 Data 包只收了前100个。默认动画表的99行覆盖正确，也不能证明
独立 ADV 入场表或选人 `stand / ready` 已接通；后者当时还没有已制替代。
入场不仅漏了5条现成动画，还漏了其独立身体模型消费者。胜利与 Last Horizon 本人的
动作则能追到默认表，不应因为另一个入口失败就笼统宣称它们也漏装。

复用时用当前资源生成入口矩阵，不照搬这些数量。至少记录：场景/状态、源
MeshArray/AnimArray/AnimSet、实际动画名、已制替代、Cook 文件、PAK 路径、运行消费者
及实机证据。**已制作、已打包、引用正确、实际播放正确**是四个不同结论。
外观开发通过后不能省掉此映射，也不要把它拖到安装失败时才第一次调查。

运行代码或配置里的字符串资源引用也属于依赖闭包。某次真实装配还发现两份开发工程
专用的材质父实例没有打包；它们由 Lua 动态加载，因此仅扫描 Cook 资产 imports 没有
发现。把这类字符串根节点一起与当前游戏 PAK、最终 MOD 清单核对，保留原批准参数和
初始化顺序；不能用一个名字相似的材质掩盖缺依赖。

| 路线 | 包内路径与入口 | 挂载之后还缺什么 |
|---|---|---|
| 原路径资源替换 | 覆盖当前游戏实际读取的精确 package/object 路径；R09.3 属于此类 | 确认当前角色/动作确实读该资源、加载优先级、版本和依赖兼容，再作实际游戏验证 |
| 新路径数据 + 零售运行桥 | 例如 `/Game/Review/...`，不碰原资源；下文 R210 历史快照采用此类 | 可在 Shipping 部署的消费者，主动加载/绑定资源，并完成动画、材质、物理、显隐和生命周期 |

按消费者逐项决定，避免二选一地重做整个人物：

1. **有原生入口且能表达目标**：沿用原路径及原生命名/引用关系。普通换装或现有道具的
   形状替换，不应默认引入每帧查角色、创建显示层及复制全部材质的运行桥。
2. **确需额外组件或控制**：例如一个独立骨架的追加物件、已有角色槽位无法承载的物理，
   或原动画没有的状态控制。先检查能否通过原生 mesh/material/动画资产与 Cook 后的
   AnimBlueprint 表达；确实仍需扩展，再实现范围明确的运行桥。记录输入、消费者、时序、
   生命周期和部署依赖。某版开发预览使用了这些技术，不等于零售游戏必须照搬其全部架构。
3. **混合方案**：主体及能直换的资源仍由原游戏加载，只为确有需要的增量功能保留扩展。
   拆除动态桥中的重复职责时，核对表情、物理、切换、分身/残影和描边都仍有实际消费者；
   不能以删掉功能换取“安装成功”。

原路径替换应核对 package 路径、导出对象名、骨架/section 与 imports。把已 Cook 的
`Review/Foo` 文件仅在 PAK response 里改名成原角色文件，不能据此断言其内部名字和引用
也已迁移；按实际资产合同重建/重定向并 Cook，或提供验证过的路径迁移证据。不要随旧工程
覆盖当前游戏的 BBS、命中数据或平衡调整。每条例外均应具体到资源与行为，避免“所有新模型
都要桥”或“有一个额外组件就整个人物用桥”的假设。

**开发效果完成不等于可发布 MOD。** R209 演示依赖 14 个查找编辑器导出 API 的驱动与
16 个独立显示层。Shipping 没有相同编辑器 DLL 接口；只 Cook 新增 Review 路径，原角色
仍使用原 consumer，继续显示 Slayer 是缺入口的结果。再打一个正确 PAK 不会补上入口。

立项早期先做一条完整的最小零售闭环：当前安装指纹 → 真实角色 consumer → 一层显示
及正确材质 → 原动画驱动 → 所需物理 → 进出场/切换显隐 → 原游戏相机看到结果。
动态方案应提早证明调度、所需 native 类和正常 GPU 提交；不能把 CPU 变形替代当作
已有 GPU 动画/形变桥完成。编辑器裸偏移、PDB guard、测试宏不能当作零售 API。
先证实这条路线，再扩展整个人物，避免最后才发现整套开发驱动无法部署。

## 1. 从真实 Cook 输出建立精确清单

R09.3 沿用 R09.2 的完整清单，仅以实际 Cook 的 WinHarmony06 更新两个原路径动画：

```text
Chara/COS/Costume01/Animation/Default/headhigh/cos800cs_headhigh01.uasset
Chara/COS/Costume01/Animation/Default/headLow/cos800cs_head01.uasset
```

挂载根为 `../../../RED/Content/`。构建器要求新旧两项的 mount 集合完全相同，并且所有
未选中条目保持原样。最终是 **1,169 个逻辑资产、2,417 个物理文件**；变更 2 资产/4 文件，
其余 2,413 文件沿用且逐项核对。703 个语音目标、已有武器和配色修复仍在完整包中。
这些是该版数量，不应写成其他项目的硬编码期望。

复用时保留以下清单字段：逻辑资产 ID、当前 consumer、Cook 源文件、精确 mount、
字节数、SHA256、选定候选、依赖提供者。一个 uasset 可能带 `.uexp`、`.ubulk`；
由实际 Cook 清单收齐，不能只复制 `.uasset`，也不能假设每项必有三文件。

依赖检查要区分包内资产、当前游戏原生提供者和 native script module。R09.3 对两项
名称带 Preview 的 stock 贴图先核对当前原 PAK 的精确 mount，再允许它们作为原生依赖；
这不是忽略所有 Preview 引用的规则。未 Cook 资产里的 editor-only import 与 Cook 后仍
存在的 native 运行依赖也不同。不要把编辑器 DLL、宏、旧 Gameplay BBS 加入运行包补缺口。

Cook 使用匹配版本的引擎和必要资产闭包，不因一次内容更新重编整个引擎/游戏。用私有
Content/Config/Saved/Intermediate/DDC，保存 Cook 命令、日志与输入哈希；由闭包得到的
Cook 输出通常大于最终选定包，打包仍使用显式允许清单。ShaderArchives 是否需要随包，
应从本次 Cook 的 shader 存储与加载合同判断，不能照另一个包的缺省。

### 动画压缩设置也是输入依赖

R210 补选人 `stand / ready` 时，首轮 Cook 虽然成功，实际 key table 却丢了原先的
停帧转折。私有工程漏掉原角色的 `CharaSelectAnimBoneCompressionSettings`，引擎回落
到默认 Constant 压缩，并按对象命名类别每5帧采样；时长也被改为帧数除以60。
只核对 NumFrames、资产路径或 Cook 返回码看不出此问题。

从当前游戏原资源读到的正确 codec 是 `AnimCompress_LeastDestructive`。补齐对应
设置、恢复两条动画的 BoneCompressionSettings，再仅重 Cook 这两条。最终输出无需
二进制改时长。这里的 codec 与采样规则是此工程的实证，不是所有 GGST 动画的通用
设置。复用时比较当前源和 Cook 后的实际压缩设置、关键帧时间、hold/step、帧数与时长；
先排查遗漏依赖，不用统一拉伸时长或换算法掩盖差异。该数据核对不代替实机播放验收。

## 2. Create / Test / List / Extract / 全量哈希

从已检查的物理文件清单生成 response，每行保持两个引号参数：

```text
"<cooked-root>/Chara/.../chosen.uasset" "../../../RED/Content/Chara/.../chosen.uasset" -compress
"<cooked-root>/Chara/.../chosen.uexp" "../../../RED/Content/Chara/.../chosen.uexp" -compress
```

命令形状如下；尖括号是本项目配置，**不是可原样运行的路径**。历史脚本附带
`-NoEnginePlugins -unattended -nop4 -nosplash`，新工具版本应核对其实际参数。

```text
<UnrealPak> <output.pak> -Create=<response.txt> -compress
<UnrealPak> <output.pak> -Test
<UnrealPak> <output.pak> -List
<UnrealPak> <output.pak> -Extract <fresh-extract-directory>
```

四个层次各自保留证据：

1. Create 退出码和日志成功；输出 PAK 的 SHA256 固定。
2. Test 无错误；它不证明消费者、视觉和缺失外部依赖。
3. List 的 mount 根、完整文件集合及数量等于允许清单；拒绝大小写折叠后的重复 mount。
4. 从最终 PAK 提取到新目录，**全部文件**集合、大小和 SHA256 等于 Cook 清单，含所有
   companions；多一个旧资产或少一个 ubulk 都失败，不抽样。

不同 UnrealPak 版本提取目录可能从 Content 内开始或带项目/Content 前缀。
R09.3 接受两种明确已知布局，均作精确集合核对。复用工具只配置一个实际观察到的
`extracted_root` 与 `mount_prefix`，不要任意去掉前缀或靠 basename 匹配掩盖路径错误。

## 3. SIG 的真实来源与发布目录

R09.3 的 PAK 是新建的；SIG 是**从 R09.2 发布目录原样复制的兼容伴随文件**，改为与
新 PAK 同名。其 SHA256 为
`0c6d3be6ddfa39ec514702881412953dc4fff1eb5e19cee1e2486a8395fdae2f`。
没有生成新的密码学签名，也不能据此宣称新 PAK 已被游戏发行方认证。这个已记录做法
不证明任意游戏或版本可以复用任意 SIG；新项目须记录实际来源、哈希和加载证据。

```text
release/
  Example_R2/
    Example_R2_P.pak
    Example_R2_P.sig
    package_info.json
    SHA256SUMS.txt
```

发布 ZIP 检查相对路径、无越界、递归可发现 PAK、同名 SIG、解压后每文件哈希。
R09.3 还做 ZIP CRC 和逐 member 哈希。ZIP CRC、PAK Test、Unverum 离线复制规则模拟、
线上 GameBanana 一键安装、零售画面是不同验证。历史 copy-rule 模拟通过，线上一键
没有做；不用它填“朋友已一键装好”。

## 4. 保护已有 MOD 的安装事务

R09.3 同时写手动加载目录与 Unverum library，二者不能混淆：

```text
<game>/RED/Content/Paks/~mods/Example_R2/     # 实际加载文件
<manager>/Mods/<game-key>/Example_R2/        # 管理器来源副本
<backups>/transaction-id/                   # 在整个 Paks 树之外
```

旧版放进 `Paks/disabled` 或 `Paks/~mods/backup` 仍可能被扫描，**备份必须在整个 Paks
目录之外**。先校验规范化绝对路径、边界与 symlink/junction，操作精确旧版目录。
不要递归删除整个 `~mods` 或清空管理器游戏配置。先读取现场，确定当前 loadout、
旧版 PAK 哈希、精确目标与实际游戏/管理器进程；历史脚本的进程名称正则不应照搬到
另一版 EXE。安装步骤在授权范围内进行，不因这个例子增加确认轮次。

R09.3 实际顺序是：

1. 要求目标新目录不存在、旧 PAK 哈希符合预期，枚举保存所有无关 MOD 文件哈希。
2. 读取并备份原始 `Config.json`，在内存产生精确的新配置。
3. 将发布目录复制到事务 staging 和 Unverum library，两处核对运行文件哈希。
4. 旧 live 目录移到外部备份，staging 移到 live；旧 Unverum library 留在原处但禁用。
5. 写候选配置，核对 installed 文件及无关 MOD 哈希；删除比较副本里的旧/新条目后，
   整份 Config 的其他游戏、设置、条目及 loadout 内容必须语义相同。

历史脚本没有自动 rollback handler，不能称为完整原子事务。复用实现可增加配置写入前
before-hash 检查和同目录临时文件替换；这是本例演练的改进。实际执行仍需记录每步状态。
恢复只触及本次拥有的路径与条目，先确认没有后续用户改动；不要拿旧 Config 整体覆盖
安装之后新加的其他 MOD。没有执行 Unverum Build 就不要写成 Build 已通过。

### Unverum JSON 字段与更新范围

这是 R09.3 保存的 schema，迁移时先核对当前版本实物。字段大小写不能改：

```json
{
  "Configs": {
    "Guilty Gear -Strive-": {
      "CurrentLoadout": "Default",
      "ModList": [
        {"name": "Example_R2", "enabled": true,
         "paks": {"<absolute-library-path>/Example_R2_P.pak": true}}
      ],
      "Loadouts": {
        "Default": [
          {"name": "Example_R2", "enabled": true,
           "paks": {"<absolute-library-path>/Example_R2_P.pak": true}}
        ]
      }
    }
  }
}
```

上面只展示字段，**不能整份覆盖现有配置**。真实更新保留其他行和未知字段：

- `paks` 的键是 **library 内 PAK 的绝对路径**，值 `true`；不是 `~mods` 副本或 SIG。
  多 PAK 同一条目包含所有实际 library PAK 键，各自 `true`。
- 旧版在 `ModList` 恰有一行；把旧版在 `ModList` 及所有 `Loadouts` 的 `enabled` 改为
  `false`。不删旧 library，不改它的其他字段。
- 新版插入 `ModList` 和**当前选定** loadout。保留 `CurrentLoadout`；其他 loadout 不
  自动加入新版。重名、旧版数量异常、active 变化应先重新读取并分析，不能重复插行。
- R09.3 核对 34 个无关 MOD 文件未变，以及 strip-old/new 后整份配置语义未变。
  这是 34 个文件，不是 34 个 MOD。

历史发布说明提醒 Unverum Build 会重建 `~mods`；新环境先核对管理器实际版本/行为。
对可能被重建的手动 MOD，应先备份并纳入管理器来源。一次手动复制与配置登记并不
证明后续 Build 会保留所有手动内容。

## 5. 可运行的合成演练与配置计划

[cook_install_demo.py](../examples/cook_install_demo.py) 使用 Python 3.10+ 标准库。
`demo` 只在**新建、尚不存在**的目录中造带标签的文本文件，演练 staging、外部备份、
library/live 两份哈希和精确配置更新；这些 `.pak/.sig` 不是引擎包或签名。
`plan` 读取用户配置与源文件，仅向 stdout 打印计划和候选 Config，**没有 live apply 命令**。

```sh
python skills/arc-mod-harness/examples/cook_install_demo.py demo .local/cook-install-demo
python skills/arc-mod-harness/examples/cook_install_demo.py --help
```

输出 `example-input.json`、`plan.json`、`result.json` 和沙箱文件树。演练安装之后再次
对其 input 执行 `plan` 会拒绝，因为新版已存在；用于真实只读计划时，复制 input 到
私有工作区并替换路径、原版/发布清单哈希和 SIG 来源，使其描述当前尚未安装的现场：

```sh
python skills/arc-mod-harness/examples/cook_install_demo.py plan private-install-input.json
```

示例计划针对 R09.3 的“一个旧版 → 一个新版，单 PAK/SIG”场景，不自动发现冲突、
枚举进程、解析 uasset imports 或支持所有管理器 schema。真实多 PAK 发布应把所有
PAK/SIG 与消费者纳入显式合同；不能只改一个 `pak` 字段就声称多包入口已验证。

已有实际 UnrealPak 提取输出可用只读全量核对入口：

```sh
python skills/arc-mod-harness/examples/cook_install_demo.py verify-extract private-manifest.json private-extracted-root
```

manifest 使用 `{"mount_prefix":"../../../RED/Content/","files":[...]}`，每个 file 为
`{"mount":"../../../RED/Content/<relative-file>","size":123,"sha256":"<64-hex>"}`。
它验证现有文件，不执行 UnrealPak，也不把提取哈希通过当作引擎或零售运行通过。

## 6. 两个真实案例的证据边界

| 证据 | Happy Chaos R09.3 | Gold R210：2026-09-21 安装快照 |
|---|---|---|
| 最终包检查 | 1,169 资产 / 2,417 文件，全量提取哈希通过 | Data 338 资产 / 677 文件，零原路径覆盖；RootBridge 3 资产 / 6 文件，均通过 |
| 加载入口 | 保持当前源资源原路径；仍需版本/实机确认 | 新增 Review 路径，需独立 Shipping 运行桥消费 |
| SIG | 复制 R09.2 兼容 sidecar | 从当前安装的 `pakchunk0-WindowsNoEditor.sig` 复制成两个 PAK 的同名 sidecar；非重新签名 |
| 安装/管理器 | live/library 哈希，Default 启用，旧版禁用，34 无关文件与配置保留 | 两 PAK + 同名 SIG，Default 中 GoldShipR210 两 PAK 启用，36 无关文件与配置保留 |
| 游戏与分享 | `runtime_playtest_performed=false`；没有本版新实机/朋友/线上一键验收 | 该安装记录独立于运行桥；此快照不证明角色、物理、表情和显隐已生效 |

R210 Cook 报告内 `installed=false` 描述**当时构建阶段**，后来安装结果另存，不能修改
旧报告来制造同一次验证。其内联 shader 和原生 Kawaii 静态存在证据只说明依赖条件，
并不证明 solver 已在零售正常运行。正式验收应关联最终 installed 包/桥哈希、当前游戏
指纹、角色/颜色/动作/场景、实际捕获与未覆盖项；没有这些证据就继续标明待验。

## 7. 独立安装与更新兼容：区分完整性和能力检查

给另一台电脑的包应包含全部实际运行文件和必要的可分发运行库，用目标游戏目录或
Steam 库发现定位安装位置。安装器不依赖作者的盘符、开发工程、Python、Blender 或 UE
编辑器。作者用于构建发布 ZIP 的工具可以依赖开发环境，接收者的安装入口不可以。
有非系统运行库时，记录来源并提供合法的离线安装途径；不能把作者机器恰好已有 DLL
当成朋友也具备的前提。管理器登记可选，实际运行内容不能依赖作者的管理器私有路径。

检查分开处理：

- **分发完整性**：本 MOD 的 PAK、运行桥、脚本及配套文件应与本次发布清单一致。
  缺文件或哈希不符意味着分发损坏，应指出具体文件。
- **现场兼容性**：游戏 EXE 哈希、Steam build 和 PE 时间戳记录为诊断信息。仅因它们
  变化就拒绝安装，会把兼容的小更新误判为不支持。实际核对用到的类、函数、字段类型、
  数组布局或资源入口；FName 名称按引擎大小写语义比较。
- **局部能力**：例如只服务某个技能的动作读取器失配，应标明该功能不可用，避免用
  无关检查挡住整个人物。不得把缺失功能悄悄描述成完整适配，也不得移除必要的布局
  判据后继续写未知内存。支持新增版本与“未来任何版本保证可用”是不同承诺。

R210 的实际失败还说明：新路径 PAK 已挂载、Lua/DLL 已执行，仍不能证明角色已替换。
加载预检通过、实际角色装配生效和画面验收应各有记录。无渲染的 bootstrap 可快速定位
接口错误；它不验证 GPU 画面、Kawaii 动态效果或实际游戏镜头。

### 加载与帧耗时也是交付结果

采用额外运行组件时，比较相同场景的原版与 MOD：进入选人、首次角色加载、进入对战、
触发带残影的动作以及切换场景。区分首次加载、后续重复加载和持续帧耗时；没有 frame-time
记录时，不把日志两个时间戳间隔当作精确掉帧时长。

R210 的一次失败运行在主角色尚未装配成功时，已经将 `REDPawnEffect` 残影对象当成角色
再次装配，产生多次同步加载。教训是按真实角色类别及生命周期选定消费者，附属特效走
自己的明确路由；不把“是 REDPawn 子类”当作完整人物实例的充分条件。失败后要恢复已改
状态并结束该次无效装配，不能反复加载同一批资源。缓存 UObject 的 Lua 包装器也不自动
等于引擎会持有该资源，应核对实际引用和垃圾回收后的有效性。

把能交回原生资源路径的加载/路由职责交回游戏，再对确需保留的组件测实际开销。性能
修复不通过隐藏必需表情、取消物理或降低用户指定画质来冒充完整效果；记录采用的取舍。

### 原生数组写入失败：资源预检没有覆盖实际装配

R210 后续三包候选在四组 Cooked morph 资源读取和初始化均通过后，真实选人仍发生
Fatal。原生 dump 将失败定位到 UE4SS `TArray:Empty` 调用元素属性
`FProperty::GetMinAlignment`：自定义数组的 inner 属性缺少有效虚表，读取地址
`0x108`。字段偏移和元素大小正确，并不等于手工构造的反射属性具备完整原生语义。
Lua fixture 也不能验证原生 allocator 或属性虚函数是否可调用。

先核对现有资源是否已表达目标行为：本例自然身体的 AnimSet 已含完整 99 条动画，
只有一条引用与普通身体不同，额外清空/重填数组完全没有必要。修复选择移除这条
数组写入路径，保留源 ExtraAnimSet，仅切换必要的对象引用并独立读回；不是放宽类型
检查后继续操作未知内存。该方案的源码修复、原生对象检查与最终实机画面仍分别记录。

出现此类崩溃时，保存 dump、最后装配阶段、准确已安装文件及管理器配置；停用自己的
运行桥，把本批原路径覆盖包移到整个 Paks 目录之外，并同步停用管理器条目。保留所有
无关 MOD。失败 ZIP 应明确撤回，不能继续因哈希、Cook 或启动检查通过而标为可交付。
下一次检查应实际走组件创建、材质绑定、形变/物理接口及清理；无渲染原生对象 fixture
能补这一层，但仍不能替代真实角色状态机、GPU 画面和游戏镜头验收。

### 后续反例：接口子集通过，真实角色仍闪现、卡顿并崩溃

R210 后来补齐依赖，手动原生组件夹具通过15显示层、77材质实例、12次材料/表情调用
及清理。实际选人仍只短暂显示正确人物，随后露出原头和中间身体。原因是源对象扫描
把同一角色下新建的披风显示组件又当成源披风，得到重复角色；失效分支每帧隐藏显示层
并清零形变。另两份实际dump定位到 UE4SS 待执行回调的 Lua registry 引用不是函数，
触发终止进程；引用失效的更深层原因尚未证明，不能与披风重复识别混为同一根因。

该夹具没有原角色完整初始化、正常动画图、完整生产tick与场景生命周期，不能因为
调用子集通过就把候选标为可交用户测试。此版已撤回，不能继续用它的接口通过记录
暗示完整零售成功。恢复开发演示外观并不等于具有普通MOD的加载行为。

作者要求的验收是：原路径PAK被挂载后，角色**首次原生加载即为完整替换人物**，
不先显示原版或错误carrier，再由脚本创建显示层或换主体。将模型、材质、已制动画和
实际消费者一次收齐到完整安装包；分阶段内部制作不能变成让作者逐个试错的不完整包。
有必要的表情/物理/饰件状态控制可驱动预先存在的原生组件，其职责必须与装配主体分开。
优先把标准显示和材质池职责交还原角色资源及Cooked动画图，再核对实际首次加载、
选人至对战、返回选人和模型切换。性能和生命周期检查应走这个真实消费者，而不是
继续增加一个避开失败阶段的夹具来替代它。

## 8. 把开发演示迁回原资源结构：已验证的作者步骤

以下 R211 步骤已完成资产作者、Cook与单包安装；随后选人 Fatal，原因与 R212 修复见第9节。
**安装核验不能代表零售运行通过。** 完整候选含
621个资源、1243个伴随文件，单PAK Create/Test/List及完整Extract哈希核对通过；已部署
游戏与管理器库，四份PAK/SIG一致。独立安装器没有游戏EXE/build白名单，不依赖作者开发
环境，旧动态装配桥保持停用。这些证据解释怎样
复用已做好的内容，不把“编辑器可播放”直接称为可发布 MOD。

### 先按原生消费者分配职责

| 开发演示中的职责 | 原路径包中的承载位置 | 必须核对的内容 |
|---|---|---|
| 多个身体显示层 | 原 body / natural-body SkeletalMesh | 实际 section、材质槽、Skeleton、两个身体各自的 AnimSet |
| 独立脸/头发/帽带层 | 原 low / high / young 三套头 | 原控制骨保留，追加显示骨；同名形变合并，原头切换继续工作 |
| 逐帧写入表情权重 | 原头部 AnimSequence 曲线与原 AB 的槽混合 | held keys、负系数、Root/Mouth/Eye/Brow 各自混合范围；重新打开后按名字匹配 Skeleton 曲线 |
| 独立头发与尾巴物理组件 | 原 head / body AB 中的 Kawaii 节点 | 当前父组件姿态、根骨、碰撞体、重置条件和真实模拟；头顶覆盖保留 |
| 运行时复制光照参数 | 原 PawnMaterials 材质池和原粒子链接机制 | 材质类别、Asano 父材质匹配、原贴图覆盖；不把固定初值当动态光照已接通 |
| 饰件显隐脚本 | 能满足需求的原模型切换或原生显隐入口 | 同一动画是否被其他动作复用；从当前游戏动作/模型入口证明条件 |

具体分层不必照搬本例。先列原角色实际消费者，再决定资产怎样组织；不要先复刻演示
组件树，再为每个差异补运行桥。

### 例：墨镜显隐可以直接复用换头

作者最终规则是“Last Horizon 使用年轻头时隐藏，其他时候都戴”。只按动画编号隐藏
不够：当前游戏的另一项动作也复用同一收招动画。只读解析当前 BBS 的全部已解码动作、
初始化 MeshSet、MeshArray 和 ADV 入口后确认：年轻头默认隐藏，只在该技能的年轻头
阶段启用，入场使用另一套高头。因此候选保留 low/high 的完整墨镜，只在 young 移除
墨镜多边形，其余头部、形变和骨骼保持。游戏现有换头同时完成显隐，无需新增控制器。

这是**本次规则和当前入口**支持的简化，不能推广成“年轻头永远等于某个技能”。未来
若游戏复用该头，应重新检查入口；不要把 EXE 哈希锁作为替代。最终同镜头验证仍要覆盖
普通动作、演出前、年轻头阶段、切回、入场和结算。

### 例：材质槽名称不一定等于光照类别

本地 ASW 工具链的 `UpdateUseMaterials` 按**材质对象名**推导 `MaterialCategory`，
不按它占据的 Shadow / Decal / Unique 槽推导。`Base` 匹配先于 `Outlin/Outline`。
因此一个同时含 `Outline` 和 `Base` 的直接分配材质可能被误分成 Base；原生轮廓参数
就不会按预期更新。中间父材质是否参与表，也要和实际直接引用区分。

实施时先保存修改后的 MaterialSet，再保存 PawnMaterials，让原生 PreSave 重建缓存；
重新打开读取**每个实际分配的 MIC 和类别**。同样核对角色选择、ADV 和所有支持配色。
不要绕过缓存用每帧参数复制掩盖分类错误，也不要假定别的引擎版本使用相同命名规则。

### 例：FBX 在 Blender 能读，不等于 UE 能正确导入

一次合并头 FBX 在 Blender 通过，真实 UE 报 No bones。实际 FBX SDK 中 Skin links
存在，但骨节点的默认 NodeAttribute 为 null；缺少 `DefaultAttributeIndex=0`。
补这一元数据后 SDK 和 UE 都读到骨，几何、曲线和绑定不需重做。诊断应检查真实消费
端的最小输入差异，不能因为另一个 importer 成功就重新猜权重或坐标。

这也不证明形变法线已正确：同一批导入会重算 morph TangentZDelta，而本模型的批准
约定是 position-only morph。依约清除这些 delta 并保存、新进程读取，保护位置与索引；
不要把本例的零法线约定强加给使用正常动画法线的其他模型。

### 例：多批 Cook 必须保留各批输出

R211 为控制 UE 命令行长度，把明确的资源清单拆成四批。四次命令都返回 0，但该工具链
会清理指定的 Cook 输出目录：后批覆盖了前批结果，最终清单核查才发现早先的动画文件
已不存在。进程成功不能替代完整的交付文件集合。

使用冻结的同一套作者资产，将每批输出到独立目录，例如 `Cook/batch_00`、
`Cook/batch_01`。各批结束后，按最终游戏挂载路径合并实际 cooked companions：

1. 每个明确替换根必须存在 `.uasset` 与该工具链实际产生的伴随文件。
2. 相同挂载路径重复出现时比较内容；完全相同只保留一份，不同内容先解决来源，不能
   以最后复制者胜出。不要合入 source 资产、开发插件或整个临时 Cook 目录。
3. 从合并后的 cooked imports 找到必要新依赖；未修改且当前游戏已提供的依赖由游戏
   继续提供。将精确文件集合打成一个 PAK，List/Test 后完整解包并核对集合与文件哈希。

独立输出目录解决的是这一工具链的清理行为，不自动授权多个进程共写工程资产。
并行作者仍需隔离写入；冻结资产的 Cook 也要确认缓存、输出和工程启动没有共写冲突。

## 9. 制作蓝图时就排除仅编辑器存在的成员

下例的具体转储、作者修复、字节码及字段审计脚本见[修复实施索引](gold-r213-fix-methods.md#8-r212-kawaii-仅编辑器字段导致选人-fatal)。

### 实例：编辑器正常，选中角色立即 Fatal

R211 原路径完整包在选中角色、模型显示前崩溃。两份转储都在蓝图虚拟机
`UObject::execStructMemberContext` 读取空指针加 `0x4C` 时失败。转储中的结构体
上下文有效；为空的是字节码携带的**成员 FProperty 引用**。不要把这个地址偏移当作
所有 UE 版本的固定值，也不要把看到 Kawaii 的名字就归因为物理求解器崩溃。

实际问题在碰撞形状的 `CollisionLimitBase.Guid`：该字段包在
`WITH_EDITORONLY_DATA` 内，编辑器有它，当前零售结构体没有。自动制作
`K2Node_StructMemberSet` 时，只列出了几项运行时成员的 `ShowPinForProperties`。
此工具链重建可选 pin 的行为是：被遗漏且符合条件的字段可能默认显示。结果本想只改
球/胶囊的位置和半径，却额外编译了对调试 Guid 的赋值。

四套头部 AB 各七个形状，共28处这种赋值；每处同时在赋值类型与成员访问操作数里
引用 Guid，合计56个无效原生字段引用。严格解析 cooked Kismet 字节码后，其首个
`R211Sphere0.Guid` 调用位置与两次崩溃栈中保存的脚本偏移吻合。转储没有完整对象
堆，没有直接读出头部实例名称；随后用当前零售原生结构体的大小、对齐和 cooked
生成类属性顺序独立重建布局，两次转储的实例成员偏移均只匹配普通 low-head AB。
这是布局与字节码的交叉证明，不是从缺失的转储堆中读出了名称。四套同类错误都需修复。

### 作者阶段怎么避免

下面是合成示意，不是可直接执行的 UE 导入脚本：

```text
CollisionShape
  Offset       runtime
  Radius       runtime
  DebugId      editor-only

只给 Offset/Radius 配置显示：不保证 DebugId 被隐藏。
明确枚举该节点的完整可选 pin，显示 Offset/Radius，关闭 DebugId。
重建并编译后，再检查生成的指令确实没有 DebugId 读写。
```

- 自动作图时，检查完整节点 pin 列表及属性标记。对于 editor-only 成员明确隐藏；
  不只依赖 UI 上没接线，也不通过删除整个碰撞或动画功能回避错误。
- 对实际操作数记录**声明它的 owner 类型 + 成员路径**。某个同名字段存在于别的
  结构体，或插件版本号相同，不能证明这个引用在目标游戏可解析。
- Cook 后解析函数的完整指令边界、磁盘脚本范围和解码后字节码长度，枚举所有
  property 操作数。不要仅在二进制中搜索字符串，或只扫 `EX_StructMemberContext`
  而漏掉赋值等其他引用。
- 将这些实际引用与目标运行版本的类型/继承字段核对。源码宏、当前运行反射记录与
  cooked 操作数共同证明缺项；只看 `.uasset` 包依赖存在无法发现这种问题。

### 修复与验收边界

优先修改作者图中这些节点的 pin 配置，重新编译、保存、Cook；不要直接十六进制抹掉
字节码，破坏跳转、脚本长度或引用表。对所有同一生成器产出的蓝图做同类扫描，保护
原动作槽、位置/半径计算、物理链和表情，限制修改范围。

本例 R212 在四套头部作者图中关闭了28个 Guid 输入。重新保存、在新进程打开并
执行碰撞计算，252项位置/尺寸检查通过；Cook 后只去除了28处 Guid 赋值，规范化
比较确认其余编译指令、常量、函数和控制流一致。合并包仅八个伴随文件改变，其余
1235个文件与修复前一致；不要为了修一个无效字段重建无关模型与动画。

全包621个资源的 imports 枚举出了全部5个 Kawaii AB、13个节点，包括尾巴。
61个函数的2382个字段引用按实际 owner/member 逐项解析，无效引用从56降为0；
13节点的默认属性与87条碰撞记录也核对了零售字段集合。尾巴使用骨骼局部静态
碰撞数据，没有同类动态字段写入，身体/尾巴 AB 字节保持不变。这种扩大检查应在
制作和 Cook 阶段完成；最终安装器只核对分发包完整性，不以旧游戏版本哈希拒绝安装。

故障字段在作者图、编辑器执行、Cook 与目标运行时四层分别核对。修复后没有无效
字段引用，证明消除了已识别的兼容性错误；**不等于整个人物已在游戏里完成运行和
画面验收**。还需验证真实角色初始化以及后续动画更新，避免再次把文件完整性或
编辑器数学函数测试当作作者已经能试用的证据。
