# R217 语音 v5：先对已安装基线求差，再撤回旧覆盖

本例延续 [R213 原路径 SoundWave 方法](gold-r213-audio-example.md)，记录一次仅更新语音的有界变更。这里公开可复用步骤、计数和相对证据标识，不分发声音、游戏资产、机器路径或私有生产脚本。

**技术状态：PASS，完整单PAK已安装。** 完整来源映射、当前安装基线、压缩音频解码、原容器字段、独立回导及交付哈希已验证。整合者已完成“合并33包新声音、删除3包旧AI覆盖”、完整封包和安装保护，详见第6节。游戏触发、混音和用户试听仍待实际反馈；此记录不代表声音或美术已获用户批准。

## 1. 变更必须相对实际安装版本计算

制作说明写着“v5相对v4撤回144条原声，恢复旧AI”。这不能直接成为安装补丁清单：目标电脑实际安装的R216使用的是R213阶段引入的v3声音。

本轮先只读核对安装凭据中的PAK与制作PAK哈希，再把R216提取结果和staging里的所有声音文件与R213交付逐文件比较。确认401套SoundWave、802个文件完全相同，且R216没有额外声音覆盖。随后才用完整v5映射对这个基线求差。

结果只有36个源WAV、36个实际包改变：33条黄金船原声、3条恢复原版Sharon。144条“退回AI”的v5文件本来就与R216的v3来源字节相同，因此本轮不重编码。入场、结算、街机等不变结论同样来自完整SHA256比较，不能仅引用制作说明中“相对v4不变”的表述。

可复用的基线选择顺序：

1. 确认正在使用的安装包身份与安装凭据，不把最近制作目录当作已安装版本。
2. 对上已安装PAK、经过提取验证的文件清单，以及本轮用于合并的基线文件。
3. 按原生包路径关联旧来源与新来源，再比较各自最终音频哈希。
4. 将差异分成“新载荷”“继续复用现有覆盖”“撤销现有覆盖”“继续由stock提供”，分别处理。

## 2. 唯一音频和游戏资产是两种数量

完整v5交付含462条唯一WAV，对应467个不同原生SoundWave包，存在5组别名额外映射。一个WAV被两个资源使用并不构成漏文件；安装清单必须保留映射中的每个真实包路径。

| v5最终内容 | 唯一WAV | 原生包 | 相对R216的动作 |
| --- | ---: | ---: | --- |
| 已有AI声音 | 362 | 365 | 保持原覆盖字节，不重编码 |
| 黄金船原声 | 33 | 33 | 写入本轮新载荷 |
| 原先已保留的Sharon／混合原音 | 64 | 66 | 继续不覆盖 |
| 新恢复的Sharon原音 | 3 | 3 | 主动删除旧AI覆盖 |
| 合计 | 462 | 467 | 最终398个声音覆盖、69个stock原资产 |

源审计逐项验证了ZIP中的462个WAV与v5成品目录字节一致，制作MANIFEST的1122项文件大小与哈希全部一致。实际编码为362个PCM16、33个PCM24、67个FLOAT32；全部48kHz单声道。不能凭上一轮的PCM16格式假设解释这一轮全部文件。

67个FLOAT32原音与各自原始OGG完整解码结果逐样本严格相等，最大采样差值为0。当前零售包里467份原OGG的哈希也全部对上制作来源，因此保留／恢复的对象有内容证据，不依赖名字猜测说话人。

## 3. 恢复原版必须撤销旧覆盖

新映射中的 `keep_original_asset` 表示最终应使用原资源。如果旧安装已经有该路径的AI覆盖，仅在新导入循环中跳过它，旧AI仍会随完整基线进入新PAK。

本例的三个对象为 `vsly603a`、`vsly603b`、`vsly603c`。每个都记录了：

- 完整原生package路径，以及R216中 `.uasset/.uexp` 的大小和SHA256。
- 当前stock两个文件的来源与哈希、内嵌OGG哈希和SoundWave布局。
- v5最终WAV哈希，以及该WAV等于stock OGG解码采样的证明。

技术交付同时准备了这3包stock原字节，形成36包／72文件的完整核验集合；这是可核对的替代复位方案。整合者最终选择从完整PAK基线中删除3包旧AI覆盖，只合并33包／66文件的新原声。删除时还必须同步显式roots、合并清单和封包响应文件，防止旧文件因另一份清单重新进入PAK。

删除操作应以“原包路径＋旧文件哈希”为条件。若待删除文件不再等于已审核的R216版本，先报告差异，不按宽泛文件名删除。保存所选33包manifest和单独的3包移除收据；不能让包含stock替代方案的36包原始manifest隐式代表最终选择。

## 4. PCM24直入一次编码，保护原cooked容器

33条新原声是用户已完成制作的PCM24 WAV。本轮直接从这些最终WAV一次编码为Vorbis q10，没有先降为PCM16，也没有追加增益、升调、变速、拉伸、裁剪、limiter或新的素材选择。已有365包覆盖完全复用；原音直接交回stock。历史v3的“+8”是半音，此轮没有重新执行它。

容器操作复用R213已经验证的inline OGG方法，并对当前每个原包重新验证结构：一个SoundWave export、一个OGG格式、声道与采样率、inline bulk flags/count/size/offset，以及尾部数据。未知布局拒绝处理，不能把某次探针得到的固定偏移用于未知版本。

替换载荷时，只允许变更：

- `.uexp` 内OGG载荷及其bulk count/size。
- export serial size和summary bulk-start等随载荷大小变化的字段。
- 下节列出的3个声音包的真实时长属性。

NameMap、imports、属性tags、其他属性值、声道、采样率和原compressed GUID保持。通过逐字节差异白名单核对这些约束。此路径没有启动编辑器重新Cook整个人物；交付沿用已核当前零售的cooked容器，不应描述成一次新的全角色Cook。

### 用户成品已变长时，同步声音自己的时长属性

v5继承了3条制作阶段已经存在的小幅时长扩展。强制旧 `Duration` / `TotalSamples` 不变，会让容器元数据与真实压缩流不一致；再次裁剪音频则会改变用户成品。

| 对象 | 原采样帧 | v5成品采样帧 | 已有延长 |
| --- | ---: | ---: | ---: |
| vsly100c | 15750 | 17688 | 1938帧／40.375ms |
| vsly101a | 23316 | 24060 | 744帧／15.5ms |
| vsly204b | 50285 | 50607 | 322帧／6.708333ms |

本轮仅将这3个包的 `Duration` 写成 `float32(final_frames / sample_rate)`、`TotalSamples` 写成其实际序列化类型的最终帧数，并读回确认。其余包保持原属性字节，包括原浮点数可能存在的一ULP表示差异。所有包都核对OGG granule总帧数、完整解码帧数和容器时长的一致性。

声音自己的元数据变化不授权修改动作触发、随机选音、模型、动画、游戏脚本、判定或其他资源。本例没有修改这些内容，也不保证有限声音池在实战中绝不重复。
