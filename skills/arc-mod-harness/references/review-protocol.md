# 什么算检查，什么算验收

## 证据类型不互相冒充

| 类型 | 能回答 | 不能单独证明 |
|---|---|---|
| AI concept | 想要的设计和情绪 | 3D 已实现、绑定正确 |
| DCC render | 当前网格、静态比例、局部姿态 | 原游戏 shader、Cook 和实际运行 |
| projection | 点的位置、轮廓和目标变化 | 双眼物理注视一致、遮挡与表情必然好看 |
| engine capture | 当前导入资源在指定引擎相机下的画面 | 游戏脚本、运行时混合、安装成功 |
| technical report | 被该测试覆盖的数值和范围 | 主观好看、所有镜头都没问题 |
| game capture | 指定包/版本/场景的游戏表现 | 所有分支、朋友电脑都正常 |
| friend capture | 指定接收环境的结果 | 所有第三方环境通用 |

## 审查页最低内容

候选名和哈希；基准/目标/当前分列；来源类型；游戏版本；角色/配色；镜头和帧号；
带过渡的视频；全画面及必要细节；此次改动、保留项、已知问题。对比必须同镜头、同时间；
不同画面不可做无说明的直接像素优劣比较。声音与原事件对齐，并标明是混合试听还是实机录音。

先让 AI 自查明显穿插/黑块/瞳孔消失，再给作者作风格选择，不把所有粗糙试错丢给人。
保留不超过三个有明确差异的方案；“A/B/C 都差不多”不能帮助人决策。

## 逐帧检查怎么做才有效

先按真实游戏镜头建立覆盖表：普通战斗、必杀、胜利、入场、头切换、极限关节与遮挡。
关键帧用于早期筛选，修复后对受影响动画用连续 contact sheet 看完整帧区间，再放大异常帧
及前后帧。最后正常速度看完整视频，确认节奏、视线、嘴型和声音。记清实际检查了哪些
帧、哪些颜色；生成了一整段图片不等于看过一整段。

不要把渲染的孤立边缘抖动和真实资产变化混淆。数值前缀不变量用于证明动画通道是否被改；
渲染像素可以因采样边缘略不同。若不是像素完全相同就不要这么声称。也不能用平均误差
很小来盖过脸上一个明显错误像素区；要看位置和具体影响。

## 反馈格式

```json
{
  "artifact": "win-C-v6",
  "camera": "win-source-camera",
  "frame": 592,
  "screen_point": [0.53, 0.68],
  "part": "character_R.black_pupil",
  "desired": "两眼略向下，黑瞳孔露出，避免内聚",
  "preserve": "上眼睑、已通过的身体、镜头和动作时间"
}
```

新手只需说话/点图，AI 负责填写。让他看一张标注回显确认对象；不要要求他先知道 bone ID。
解决反馈时链接新候选和复查结果。CLI 的 `resolve` 要求具体替代 artifact，`decision`
拒绝接受仍挂着未解决反馈的同一审查阶段。记录不是自动验证问题真的消失。

## 版本选择与范围

作者选 C 后 A/B 保留，运行清单只选 C 与 shared。选择最终外观不等于批准重新改身体。
文件、输入、关键 metadata 或选项变化后旧审查作废。已通过的 release、安装与图片分别
绑定同一版：不要拿新图片搭旧 PAK，也不要把旧游戏截图算到新版的运行通过记录中。

当人说“没问题，打包吧”，在已有授权范围执行打包；当只说“C 好看”，只记录该外观选择，
不捏造其他阶段的认可。人暂时不回应时继续独立技术工作，保留待选状态。
